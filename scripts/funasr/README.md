# 拜访录音转写（2026-11-17）

本轮仅转写原文，不生成摘要、不调用付费 AI、不判定内容相关性或拜访有效性。销售录音文件仍由 Sales 对象存储管理；FunASR 不持久保存音频或原文，不连接业务数据库。

## 已部署实例

- Ubuntu 22.04 / x86_64，4 vCPU、7.6 GiB RAM、无 GPU。
- `/opt/rigour-funasr`，Python 3.10 虚拟环境，依赖固定于 `requirements.txt`。
- `rigour-funasr.service` 已设开机启动，单 worker、CPUQuota=100%、MemoryHigh=1200M、MemoryMax=1500M。
- 仅监听 `127.0.0.1:18087`，不开放公网识别端口。凭据位于 `/etc/rigour-funasr.env`（root 0600）；不要输出或提交该文件。
- 带字词时间戳的 Paraformer ONNX int8 + CT-Transformer 标点 + Pyannote 3 分段 + 中文 CAM++ 说话人特征，无 PyTorch、无通用大语言模型。模型来源及 SHA256 见 `models-manifest.json`；原先不带时间戳的 ASR 已被替换。

```sh
ssh -o ControlPath="$HOME/.ssh/rigour-asr-%C" -O forward \
```

端口转发已经建立时不要重复添加。SSH 断开后，本地识别会重试并显示任务状态；恢复通道后继续。正式服务器部署后，Sales 使用受限内网服务地址或同机 loopback，使用环境变量覆盖地址，并保持认证；不依赖开发电脑。

现有 IDEA `SalesApplication` 环境变量增加：

- `RIGOUR_SALES_ASR_ENABLED=true`
- `RIGOUR_SALES_ASR_BASE_URL=http://127.0.0.1:18087`
- `RIGOUR_SALES_ASR_TOKEN`：与服务端相同的私密令牌。

本地 `outputs/funasr-runtime/idea-sales-environment.txt`（忽略提交、0600）保存保留原六项变量后的完整 IDEA 环境变量文本。用户可在本机终端执行下方命令，再粘贴到现有 Sales 运行项的 Environment variables 输入框；不要发到对话中：

```sh
pbcopy < outputs/funasr-runtime/idea-sales-environment.txt
```

按工程 AGENTS.md，由用户在 IDEA 重启 Sales；CRM 展示字段修改也需重启现有 CRM。其他服务不需要重启。

## 流程与约束

1. Sales 校验原录音、保留原始文件。规则开启语音转写时，按 `(tenant_id, clip_id)` 幂等入队。
2. 数据库任务租约防止重复领取。每 5 秒领取一段，HTTP 推理在事务外执行，8 分钟租约、420 秒读取超时。仅处理已结束（CHECKED_OUT）的拜访，按片段顺序处理；同一拜访只能有一个有效租约。
3. FunASR 最多接收 25 MiB、约 10 分钟的一段录音，转换为单声道 16kHz。先合并语音区间，以最多 30 秒核心窗口、两侧各 2 秒上下文转写；按字词时间戳去重，再按语句声学特征对齐说话人，不再按说话人边界切碎文字。满负载返回 429，临时文件自动删除。
4. `sales_recording_analysis` 保存原文、时间段、`asr_model`、请求标识和状态。字词时间来自 ASR 模型，不是人工校正；新增标点必须保持识别文字不变。保存匿名 `speakerId`；无法可靠区分或重叠讲话保留空编号，不虚构身份。
5. 网络/忙碌失败退避重试，最多 5 次；解码失败转 FAILED。过期租约结果不能覆盖新任务。无语音时保存成功的空原文，手机显示“未识别到清晰语音”。
6. 转写成功通过现有版本化 CRM 证据 Outbox 同步技术证据，但不构造 AI 内容结论。既有规则要求内容审核的拜访继续待核验，主管审核路径保留。
7. V39 新增模型字段、将摘要标为未请求，并一次性重发已完成拜访的最新证据；不修改历史 Flyway。
8. `sales_visit_speaker_context` 按 `(tenant_id, visit_id)` 保存匿名特征和版本；每段使用前段上下文，事务同时提交上下文和原文。并发领取、过期回调或事务回滚不能使编号串位。特征不进入手机/管理端接口，不跨拜访使用；未使用另一套前端缓存或识别模型。
9. V40 创建上下文表并将现有已结束录音在原任务行重新排队，补充说话人；不为 App/后台创建副本。A/B/C 是编号展示，具体身份未经确认。
10. 公海/私海展示当前归属下最近已提交拜访，不把待核验当作未拜访，也不增加有效拜访次数；重领后不沿用上一任归属的提交状态。

## 初步实测（仅转写版本，升级前）

使用现有 Redmi DEV 录音，不是人工生成的效果样本：

| 录音长度 | 服务端处理 | 本机到服务器往返 | 说明 |
|---|---:|---:|---|
| 193.60 秒 | 8.248 秒 | 8.349 秒 | 首次请求 |
| 193.60 秒 | 7.962 秒 | 8.095 秒 | 再次请求 |
| 299.776 秒 | 7.247 秒 | 7.316 秒 | 含较多静音 |

加载后常驻约 414 MiB，测试进程峰值 928.7 MiB；测试后 systemd 记账约 624 MiB，共享服务器仍约 1.7 GiB 可用。当前单路可运行，不代表多人并发容量已验收。以后扩容需用真实连续交谈和高峰任务量测试排队耗时。

能辨认部分申请资料、退款等句子；背景声音、远处讲话、人名有明显错字。没有人工逐字参考稿，不报告准确率；不能用此次转写直接自动判定有效拜访。官方前端含 dither，重复识别细节可能略有差异，数据库保留本次实际输出。

基准原文和 SHA256 保存在本机忽略提交的 `outputs/funasr-runtime/benchmarks/`，不放入代码仓库。识别测试脚本 `benchmark.py` 只打印时长和字符数量，原文仅写入指定的 0600 文件。

| 现有录音 | 说话人区分加转写 | 测试进程峰值 |

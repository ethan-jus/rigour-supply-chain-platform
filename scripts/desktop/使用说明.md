# 台式机 DEV 部署说明

拉代码、测试、构建、运行、数据库和备份均在台式机 192.168.12.7 的 D 盘完成。Mac 只用于日常写代码和远程操作，不是部署依赖。

## 目录

| 用途 | 台式机目录 |
| --- | --- |
| 中文入口和操作记录 | `D:\RigourDev` |
| 构建日志 | `D:\RigourDev\logs\build` |
| 发布包与工具下载 | `D:\RigourDev\downloads` |
| 云数据库完整备份 | `D:\RigourDev\backups\cloud-import` |
| 构建网络配置 | `D:\RigourDev\config` |
| Git 项目源码 | `\\wsl.localhost\RigourDev\srv\rigour-dev\src` |
| 应用配置、密钥、发布版本、回退备份 | `\\wsl.localhost\RigourDev\srv\rigour-dev\apps` |
| 中间件 Compose 和配置 | `\\wsl.localhost\RigourDev\srv\rigour-dev` |

Linux 文件实际保存在 `D:\RigourDev\wsl\RigourDev\ext4.vhdx`。不要手动移动运行中的虚拟磁盘，通过上述共享路径查看文件。

## 操作

首次把 `entry.sh` 安装为 `D:\RigourDev\scripts\app-entry.sh`，把 `一键部署.ps1` 放到 `D:\RigourDev`。日常在台式机 PowerShell 执行：

```powershell
# 从 Git 拉最新 dev、测试、构建并部署
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1
# 只构建，不更新应用或业务数据库
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1 build
# 状态、日志
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1 status
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1 logs
# 应用回退，数据库及配置必须匹配旧版本快照
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1 rollback -Version 版本号
```

流程：Git fetch 并只快进更新 → 部署脚本测试、后端 Maven verify → 门户 lint/类型检查/测试/desktop 构建 → 本机发布包校验 → 现有13个领域库、配置和密钥备份 → 准备本机配置 → 按依赖顺序启动 → 全部服务健康检查。任何构建失败均不更新应用。脚本不自动提交、推送或覆盖未提交代码，开发修改需先正常推送到 dev。

门户镜像会将公开静态目录规范为 755、文件为 644，不放宽配置或密钥目录权限。发布和回退都检查入口 JS/CSS 的状态、类型及非空内容，不能仅凭首页 HTTP 200 判定可用。

拉代码和下载依赖需要台式机 VPN 开启，代理由 `config/build-proxy.env` 与 `config/maven-settings.xml` 配置，只作用于构建，不注入应用。启动已有服务不依赖 VPN 或 GitHub。

## 首次迁移

旧服务器全部 `rigour_*` 项目库独立执行结构与数据完整导出/导入，包括历史备份库、视图、触发器、存储过程和事件定义。保留原始压缩备份及 SHA256，完整验证后才生成 `backups/cloud-import/迁移验收.json`。不迁移 MySQL 系统账号，不触碰其他项目数据库，不停止或改写云端服务。导入前备份台式机现有库，目标账号使用本机密码重新授权；克隆的外部同步任务保持关闭，防止自动回写原系统。

缺少真实迁移验收时停止发布，不能以空库、部分备份或手写标记绕过。日常更新不会重复迁移，不自动执行 Flyway repair 或数据库回退。开发账号在完整导入后单独创建并写入台式机本地中文配置，不提交到 Git。

IAM 历史 V52 的状态值兼容由新增 V51.1/V52.1 完成，V75 的菜单唯一编码/外键兼容由 V74.1/V75.1 完成，所有已执行文件保持不变。首次发布先备份本机 IAM，再由 `migrate-iam-compat.py` 核对待执行列表，仅一次性补齐这四个版本；不会全局开启 out-of-order。已完成补充迁移后，日常启动继续使用原默认严格顺序。其他环境升级须先备份、核对这四个待补版本，再由迁移负责人执行同等受控流程，不能直接改旧文件或 repair。完成后资源约束恢复为 ACTIVE/DISABLED，销售看板恢复规范 ID，迁移窗口中的临时代码和重复 ID 会清理。

## 当前脚本范围

默认发布 IAM、Gateway、门户和 `service_catalog.py` 中12个业务服务，入口 `http://192.168.12.7:5100`，IAM 为 `http://192.168.12.7:26881`。桌面使用独立 OIDC 客户端 `rigour-portal-desktop`，保留原客户端。开发使用 HTTP，真实登录、PKCE、签名和权限检查不关闭。销售工作台是独立前端，不属于微服务发布清单。

业务服务顺序：Settings 26892、HR 26889、CRM 26883、ERP 26884、Order 26885、Sales 26886、AI 26887、BI 26888、City 26890、Channel 26891、Collaboration 26893、Integration 26882。每项都检查 `/actuator/health` 的 JSON `status=UP`，不只检查 HTTP 200。真实业务与外部供应商仍须分别验收。

可以显式选择部分业务服务，始终包含IAM、Gateway和门户；不允许省略当前版本已经部署的服务，防止容器遗留：

```powershell
powershell -ExecutionPolicy Bypass -File D:\RigourDev\一键部署.ps1 -Services settings,hr,crm,order,sales,ai,bi,city,channel,collaboration
```

ERP和Integration需要先在 `/srv/rigour-dev/apps/config/external.env` 配置真实的 `RIGOUR_ERP_PRODUCT_MEDIA_COS_{REGION,BUCKET,SECRET_ID,SECRET_KEY}` 和 `RIGOUR_INTEGRATION_PRODUCT_MEDIA_COS_{REGION,BUCKET,SECRET_ID,SECRET_KEY}`。这是变量名列表，不是可直接粘贴的花括号语法。不得填假值跳过启动检查。每个容器仅注入本领域凭据，不拿到root或其他领域密码。配置不进入Git。

协作库缺失时生成独立账号及本机随机密码，不改已有账号密码。协作HTTP路由已接入Gateway；LiveKit会议媒体与WebSocket端到端链路单独验收，不把聊天列表接口可用当成会议可用。LiveKit可选配置 `RIGOUR_LIVEKIT_URL/API_KEY/API_SECRET` 也只在本机外部配置文件维护。

业务服务的数据目录为 `apps/data/服务简称`，配置为 `apps/config/服务简称.properties`，凭据为同名 `.env`。首次自动生成配置，之后保留已有properties；更新配置前先备份。克隆的订货宝定时同步、媒体worker、BI自动刷新及临时公开打卡入口默认关闭，不会因发布自动写入外部系统。普通业务API仍访问真实本机数据库。

`apps/releases` 保存版本，`apps/current` 只指向全部选定服务健康检查成功的版本；`apps/config`、`apps/keys`、`apps/backups` 保存本机配置、密钥和发布前备份。本机文件管理配置，不加载指向旧云端的 dev/local 覆盖层；服务注册到本机Nacos，不代表已把配置发布到Nacos。

应用Compose现在包含两个文件，手动操作须同时指定 `-f compose.yaml -f compose.business.json` 并设置 `RELEASE_ID`；优先用中文入口查询状态、日志和回退。仅执行旧的 `docker compose ps` 不会显示新业务清单。

发布备份为 `apps/backups/版本号/business.sql.gz`，包含当前已存在的领域库，配套 `备份记录.json`、config、keys和middleware.env。gzip完整校验后才正式命名。自动回退会核对所有领域迁移状态、配置哈希和服务范围；拒绝回退到缺少全域快照的旧三应用版本，不自动回滚数据库。

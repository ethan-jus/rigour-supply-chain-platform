# 经营看板 BI 库表与每小时同步

> 2026-09-23 后续口径修正：经营城市改为销售部下的城市部门，当前 17 城，金额按订单销售所属城市部门。默认目标按城市逐月累计；经营总览已改为连续滚动长页。下文保留当时的实施记录，当前口径、同步及验证以 [经营城市部门修正](BI_OPERATING_CITY_DEPARTMENTS_2026-09-23.md) 为准。


范围：已确认的经营总览、城市经营、销售业绩三套看板。服务为 `rg-scdp-bi`，开发库为 `rigour_bi`；业务库不改表、不回写、不重新拉订货宝。

## 库表评估与改动

保留领域 API → BI 源镜像 → BI 事实/预计算的架构。看板在线查询只访问 BI 库。当前数千订单、数万订单行，以事实表聚合即可支持自定义日期、城市、销售、品类、商品、型号；不另存按月计算的百分比，避免跨月汇总与历史补款失真。

| 查询维度 | BI 数据与口径 | 优化 |
|---|---|---|
| 全国/城市/销售交易排名 | `bi_sales_order_fact`，订单日期、折后应收，排除删除/取消 | 已有租户+城市/销售+日期索引 |
| 全国/城市/销售到账排名 | `bi_sales_payment_fact`，到账日期，使用订单归属销售 `owner_staff_code` | V22 增加租户+城市+到账日期、订单关联索引 |
| 所选月份订单回款率 | 同批订单 `SUM(paid_amount)/SUM(payable_amount)`，累计已收随后续补款更新 | 不以到账日期截断订单累计回款 |
| 历史订单回款率 | 全历史有效订单累计已收/应收，仍保留租户与授权范围 | 不套用所选订单月份 |
| 商品/品类/型号交易额 | V22 `bi_dashboard_order_product`，一订单一商品行 | 预分摊整单折后金额和累计已收，带商品/品类索引 |
| 商品/品类/型号到账 | V22 `bi_dashboard_payment_product`，一回款记录一商品行 | 按实际到账日期索引，不将订单日期当到账日期 |
| 复购率 | 本期复购客户/本期成交客户，复购需要期初之前有有效订单 | V23 `bi_dashboard_customer_history` 存首次有效下单日；主键查找，跨城市/销售历史不被当前权限过滤截断 |
| 交易/回款目标完成率 | `bi_business_target` 的 `SALES_AMOUNT` / `RECEIPT_AMOUNT` | 按月目标汇总；未配置保持未知，不能显示成零目标 |

商品交易额按 `单价×数量 / 全单订货金额` 分摊整单应收；回款按同一比例分摊。最后一行吸收六位小数尾差，逐订单与逐回款金额守恒。缺明细、分母无效、回款未关联有效订单时保留 `UNALLOCATABLE` 记录及金额，不丢弃，不虚构商品归属。

`bi_dashboard_product_snapshot` 保存已发布批次和同步时间。商品订单分摊、到账分摊、首次下单摘要在同一事务内替换；失败保留上一个完整版本。新商品表保留 `order_id`：以后查询接口必须关联经过 `BiScopedQueries` 过滤的订单/回款事实，不能仅凭前端传入销售或城市授权。首次下单摘要不包含历史金额与销售明细，只用于已经可见的本期客户判断复购。

新城市回款及 `RECEIPT_AMOUNT` 目标使用订单销售归属；原独立“收款经办人”报表仍保留原口径。商品预计算表是查询数据层，本次没有改销售主图的前端加载接口；不能把 SQL 校验当作销售页面全字段已联调验收。

## 同步与运行规则

- 复用 `SupplyDashboardRefreshService`，任务代码 `SUPPLY_DASHBOARD_HOURLY`。`fixed-delay-ms=3600000`，即每轮完成后间隔 1 小时；服务启动后 60 秒自动执行首轮。
- 本机 `local` 配置启用。共享 `dev` 默认关闭，但可通过 `RIGOUR_ANALYTICS_SUPPLY_REFRESH_ENABLED=true` 显式启用；个人实例继续留在 `ethan-local` 命名空间。
- 调度范围：客户、城市字典、订单、订单明细、商品/品类/规格、回款、库存/流转、对账，以及看板商品/复购预计算。HR/拜访有独立人员刷新，销售工作台不可用不会阻断财务看板任务。
- 通过现有受信领域只读 API 同步，不跨业务 schema 直接查询。未变化数据集按版本跳过；变化数据集当前仍整批分页拉取，校验版本与租户后事务发布。不是逐条事件增量同步。
- 当前规模下每小时从本地源镜像全历史重算事实，覆盖历史订单改价、补款、商品行修改及删除；物理删除通过已成功发布的完整镜像退役旧事实。
- JDBC 启用 `rewriteBatchedStatements`，加速分页批量写入。每次运行使用租户锁，源与运行记录保留水位、状态、数量及错误；不手工改检查点或任务状态制造成功。
- 首轮包含历史镜像补齐，耗时较长。源版本发生变化或请求失败会保留原镜像并记录失败；不会发布半份源数据。

## 验证与边界

自动化覆盖真实 MySQL 迁移/分摊、金额精度、幂等、跨期到账、历史更正/删除、事务回滚、首次下单摘要及授权后的跨城复购；运行证据见工作区 `outputs/bi-hourly-sync-20260923/`。

目标配置表当前为空，需要录入真实月度目标；同步不会自行生成目标。未分摊金额必须在产品维度展示为待核对。源数据质量问题应修在对应业务服务，再由下一轮同步更新 BI。

本机进程关闭、电脑睡眠或断网期间任务不会继续运行；本次不是共享服务器/生产部署。迁移仅新增 BI 表和索引，未改业务库结构，未提交或推送其他任务代码。

# 货拉拉接口能力核对与接入方案

版本：V2.5 待确认稿　核对日期：2026-11-09

本文供开发实施使用。产品页面以同目录《产品需求文档》V2.5为准；本轮仅修订方案和演示原型，不修改正式服务、权限或数据库。

## 1 本次核对结论

1. 用户本次提供的链接 type=3、id=23 是“货拉拉APP业务”的查询订单详情，方法为 u-order-detail。它不是企业版 e-order-detail 的另一个链接。
2. 用户提供的《货拉拉API对接百问百答》正文标明企业版；《API实操指南》包含两类文档链接，不能把所有字段视为同一响应结构。
3. 本系统目标是企业平台已有订单、平台员工与本系统订单／员工关联。建议企业版 e-order-list、e-order-detail、e-staff-construct、e-staff-detail 为本期主链路，不能只凭 u-order-detail 完成企业订单及员工接入。
4. APP业务接口作为已核对的另一套能力记录，暂不同时接两套账号，也不在业务页面增加接口类型选择。最终必须以实际开通应用及授权账户核验；若企业版未开通，不自动切换APP接口冒充全企业数据。
5. 暂不设计本系统新的业务主管、财务、接入管理员角色或权限矩阵；沿用现有登录、菜单及租户校验。这不取消货拉拉本身的应用开通和账户授权要求。

## 2 官方接口对照

| 用途 | 企业版主方案 | APP业务接口 | 本期处理 |
| --- | --- | --- | --- |
| 查询订单列表 | e-order-list；type=2&id=10 | u-order-list；type=3&id=27 | 根据实际开通产品使用对应适配器，不共用响应解析 |
| 查询订单详情 | e-order-detail；type=2&id=9 | u-order-detail；用户链接type=3&id=23 | 企业列表对应企业详情；APP列表对应APP详情 |
| 平台员工目录 | e-staff-construct；type=2&id=151 | 本次APP列表及详情文档没有员工目录字段 | 企业版同步员工；不能用订单联系人伪造员工目录 |
| 平台员工详情 | e-staff-detail；type=2&id=154 | 本次APP两份订单契约未提供对应能力 | 补齐user_id、staff_id、部门资料，再做HR映射 |

企业列表说明可查近3年，详情说明只查近1年；APP列表说明近3个月。企业列表和APP列表每页最多20条，APP列表明确不建议深分页。这些是文档能力上限，不等于当前账户已获全部范围或历史记录一定可取。

仅有详情接口不能枚举所有订单。必须先用对应列表取得平台单号，再按单补详情。实际企业平台网页、企业APP及各下单账号产生的记录，须用样本与平台核对是否都在授权查询范围，不能预先保证跨账号全覆盖。

## 3 必要接入流程

### 3.1 应用和账户准备

- 开发者注册、创建应用并完成平台审核，获取服务端使用的应用凭据。
- 在平台应用详情确认已开通订单列表、订单详情；需要人员关联时一并开通员工目录、员工详情。只做数据接入，不要求开通叫车、计价、支付、取消、开票等写操作。
- 由货拉拉有相应查询范围的企业账号完成授权。PDF提及企业详情可能受超管／白名单限制，实际以本企业账号测试为准；不能据此在本系统新增同名超级管理员角色。
- 仍需OAuth账户授权。app_key标识应用，不能代替access_token读取账户私有订单。
- 代码处理授权跳转、回调校验、短期code换token、加密保存及令牌刷新，页面不输入密钥、回调地址、环境或凭据引用。
- 指南写有code和token期限；实现以正式授权接口返回的期限为依据，不把“3个月”等写死为定时器。刷新后原子替换新令牌，避免多任务并发刷新导致旧令牌失效。

### 3.2 首次订单同步

1. 选择业务日期范围；后台按对应列表支持的时间条件拆成小窗口，每页不超过20条，直到该窗口结束。
2. 每取得一页，先在Integration保存源内容，再让Order保存／更新本地平台订单及其对应的物流运输记录。
3. 默认单据状态为待确认；平台状态独立保存。没有订单关联、没有员工映射、金额缺失、取消或进行中都不影响先展示。
4. 再逐单查询同一产品族的详情，保存路线、费用分项、司机、回单及其他取得的字段。单笔详情失败只标记该单待补，不回滚已成功列表。
5. 页面列表和详情均从本地读取，不在列表打开时逐行即时查货拉拉。
6. 超过详情历史范围仍允许保留列表数据，详情明确暂缺；不能反复无效重试，也不能自动用当前费用或相似订单补历史金额。

### 3.3 后续同步

企业列表提供用车时间、完单时间等筛选，本次文档未见“按最后修改时间筛选”的请求条件。不能直接把上次同步时间当作更新时间游标，否则旧订单后续加费、退款、账单变化可能漏掉。

建议采用以下组合，频率及回看窗口按真实配额配置，不向业务暴露技术参数：

- 按用车时间滚动回查近期窗口，重叠范围依幂等键去重。
- 对本地未完单、账单待处理、详情失败记录，使用原单号补查详情。
- 对已完成但仍可能发生账单变化的记录保留回看期，并提供按月补同步或按单重试。
- 分页期间平台总量变化时允许边界回扫，以源单号去重，避免只信一次total而漏单。
- 报告新增、更新、无需更新、列表已保存、详情成功、详情待补及失败，不能仅显示“同步完成”。

### 3.4 回调的适用边界

指南说明可通过notify_url接收状态或账单事件，且演示从下单请求传入回调地址。当前项目读取已有平台订单，不从本系统叫车，因此不能据此承诺既有网页／APP订单都会推给本系统。

本期以查询同步为可运行基线。若平台确认现有企业订单也支持统一订阅，后续接入回调作增量触发：先验签、按serial_no去重、可靠入队，再补查详情；按规范响应。回调与查询共用相同平台单幂等键。未确认覆盖范围前不取消定时补查；回调不能直接修改已确认成本。

## 4 已核对字段映射

以下保留字段标识供开发查阅，不在业务页面展示。

| 本地业务含义 | 企业版列表／详情 | APP详情 | 处理原则 |
| --- | --- | --- | --- |
| 平台订单号 | order_display_id | order_display_id | 全程字符串；请求契约要求int64时精确序列化，不能经过浮点数 |
| 企业与下单用户 | 列表ep_id、user_id | 本次详情契约未列企业员工身份 | 不能从联系人姓名推断user_id |
| 用车／创建／完成时间 | order_time、create_time、complete_time；列表有完单时间字段 | order_time、create_time、complete_time为时间戳 | 企业字符串时间与APP秒时间戳分别解析，统一展示北京时间 |
| 配送路线 | addr_info_arr | addr_info | 保存全部点及原始顺序，不只取第一或最后收货点 |
| 点位联系方式 | contact_name、contact_phone_no等文档字段 | contacts_name、contacts_phone_no | 不与下单联系人或员工身份混用 |

| 应收／应付参考 | 以企业真实回执确认最终费用字段和优惠处理 | receivable_total_fen（平台实际应收） | 不把文档之外的字段当作已具备，也不保证与Excel同列同口径 |
| 已付／未付／退款 | 详情paid_amount、unpaid_amount、refund_amount；列表paid_amount_fen | unpaid_price_fen；本次未列与企业等价的已付及退款总额字段 | 无字段不推算；不能把订单总额减未付直接宣称实付 |
| 费用明细 | order_price_arr的bill_name、type、price_fen、img_urls | price_info的bill_type、bill_type_name、amount_fen、img_urls | 按来源适配，保留正负号、类型、凭证；保留未知新费用类型 |
| 赠金及优惠 | bonus_pay_fen、列表coupon_fen、详情费用项 | 本次契约没有全部等价字段 | 订单金额、优惠、赠金、退款各存各的，不能重复扣减 |
| 司机及车辆 | driver_info，完成72小时后不再返回 | driver_info，车牌说明为脱敏值，号码有类型 | 按实际返回展示脱敏或虚拟号，不承诺完整真实号码与车牌 |
| 回单 | receipt_url、条件返回的receipt_info | receipt_url | 非必有；外链过期与无回单分开，按授权处理留存 |
| 平台员工 | 员工目录及员工详情 | 不能由APP订单联系人替代 | 与本系统员工建立独立关系，不创建HR同名重复员工 |

企业详情的主体位于data.order_detail_item.order_item，并有司机等相关结构；企业列表是data.order_arr，APP列表是data.order_list。响应层级、字段类型都应分别做契约测试，不能只替换api_method。

企业详情及列表的旧pay_status已经在当前文档标记停止维护；不能只靠旧支付状态断言已结清。优先保存现行金额字段和支付方式；月结未付不等于没有运输成本。

司机装卸货照片、实际里程等在企业详情明确注明需商务申请，不作为本期必有字段。一般回单也受真实订单和外链时效限制。指南与当前API存在审核时长、费用申诉、金额字段等表述差异时，按当前对应接口和实际回执核验，不照抄全部常量。

### 4.1 V2.5 账单和凭证的使用

企业详情已核对的`order_price_arr`包含`bill_name`、`type`、`price_fen`、`img_urls`；`paid_amount`、`unpaid_amount`、`refund_amount`及`update_bill_time`分别用于付款汇总及账单时间。原始类型与金额均保留，展示层按已核实语义显示抵扣负号，不对未知类型自行推导正负。旧`pay_status`、`tax_value`不作为当前付款或税费的唯一依据。

费用数组可有同类型多项，不能用类型作为唯一键覆盖；明细与汇总可能存在层级，不能把平台全部金额机械相加。已支付不生成另一笔成本，优惠、退款、赠金不在来源总额上未经核对再次扣减。截图137.64元的组合仅作为样例算式，不能代替实际接口对账。

`img_urls`证明契约存在图片地址字段，不证明本企业每笔单均有凭证、地址永久有效或已取得长期留存权限。正式接入保存源关联并按实际授权补取文件；凭证失败独立重试。详情汇总、分项、凭证只读，原型查看／下载使用明确标注的示例文件。

## 5 人员与业务订单关系

### 5.1 平台人员识别

企业员工目录返回人员code；员工详情返回staff_id、user_id、staff_name、phone_no、depart_id等。建议链路为：平台订单user_id → 企业员工详情对应的staff_id → 本系统员工ID。

手机号一致仅作推荐，由业务确认；同名、缺手机、离职或员工目录权限暂未开通时保留待关联，不阻断订单同步。下单contact_name及配送点联系人都不能当作已确认的平台员工身份。

员工映射关联一次可用于同一企业该员工的多张订单；不把货拉拉部门覆盖HR部门。若仅具备APP业务接口，保留自动取得的下单联系人信息，但员工目录及员工级映射能力必须标为未具备，不能宣称已自动取得平台员工。

### 5.2 业务订单关联与成本

人工选择运输类型并锁定销售单／调拨单／其他订单；保留现有多对多关联。平台没有本系统单号时只能推荐候选，不能精确自动关联。

物流归属仍取关联销售单的部门、业务员；平台员工映射用于追溯下单人，不替代销售归属。采购成本仍取收货仓库对应部门。多单分摊时平台费用只计一次，已确认成本不被同步直接改写。

## 6 精简持久化与现有代码差异

继续复用Integration源数据、同步任务与员工映射，Order平台来源记录、物流主记录和审计。独立保存业务订单关系，避免把生成费用单当作同步入库前提；不新增角色、权限配置表或平台部门管理模块。具体表设计见《数据接入与保存说明》。

| 已有代码基础（本轮只读核对） | 符合之处 | 正式实现需补齐 |
| --- | --- | --- |
| HttpHuolalaGateway仅允许e-order-list、e-order-detail及两个人员方法 | 与企业只读方案一致 | 按真实响应核验签名、金额、历史范围、配额及刷新 |
| HuolalaService先取企业员工目录与详情 | 具备人员映射基础 | 员工接口失败不得阻断订单主同步；user_id／staff_id对应需验证 |
| 订单循环取得列表及详情 | 有接入编排基础 | 列表先提交、详情失败显式标待补，不能吞异常成空对象并称成功 |
| 来源记录与cost_id绑定 | 具备源单追溯 | 解耦本地展示、人工关联与费用确认；同步后直接进统一主列表 |
| 已有权限节点及上下文校验 | 登录、身份、租户边界存在 | 本期不新增角色映射，不改已执行迁移，不全局移除鉴权 |

## 7 实施顺序及核验

1. 先确认产品文档、统一主列表及字段；不先大改正式业务。
2. 开通实际应用、完成授权，核对企业网页订单是否能被对应账号查到，核对员工目录及历史范围。
3. 用完整原始回执完成适配契约测试、精确金额和长单号检查；接通列表先保存与逐单详情补齐。
4. 接入两类人工关联、手动登记保护、去重、自定义导出与已有状态流程。
5. 对照同一平台订单的网页、API、本地详情及导出，确认金额、优惠、支付和退款各口径；再核对已确认成本及部门／业务员分摊。
6. 若追加回调，先证实现有平台订单覆盖范围，再补回调验签、重放去重与补查，不把“能配置回调”当作历史全量同步成功。

待外部确认项：实际应用业务类型与接口权限、授权账户覆盖范围、网页既有订单可查询性、最终费用口径、回调覆盖范围、真实配额、图片及回单留存权限。以上放接入核对清单，不在普通业务页面堆放技术说明。

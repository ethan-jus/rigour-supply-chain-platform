# 货拉拉订单同步与本地保存说明

版本：V2.6 实施说明　日期：2026-11-10

本文供开发实施使用，不在业务页面展示。主列表沿用“物流运输记录”，同时包含货拉拉同步和手动录入，不新增平台订单主入口。产品主流程及页面以同目录《产品需求文档》V2.5为准。V2.5已按确认方案进入实施；设计要求与当前验证范围分开记录，详见第11节。

本期不新增岗位角色或权限矩阵，沿用现有身份与租户边界；不修改已执行的权限迁移，也不全局关闭鉴权。外部应用权限及账户授权仍按货拉拉要求取得。

接口族、已核验字段及限制以《接口能力核对与接入方案》为准。本期建议企业版，不把APP详情字段直接用于企业响应。

V2.3补充：货拉拉同步来源自动关联物流公司字典中“货拉拉”的编码，展示名称由字典解析；不依赖平台额外提供物流公司名称，不让业务重复选择。查询、详情、导出采用相同口径。手动记录保存业务实际选定的物流公司编码，不因使用同一编辑组件而覆盖为货拉拉。编辑平台记录仅更新允许的本系统字段，保留来源、平台编号、费用、路线和源备注。

V2.4补充：发货信息在新增、编辑、详情统一展示。手动记录保存所选发货仓库编码及发货方、联系人、电话、地址快照，不用固定仓库兜底；原业务单无仓库时允许选择或填写实际厂家。平台记录按完整路线保存、展示发货点，不按名称猜配本系统仓库。发货资料继续归物流记录所有，不新增独立发货信息表。

## 1 数据流

货拉拉来源主档和手工运输费用在统一物流运输记录中呈现。每个货拉拉订单同步后自动建立或更新一条本地运输记录，初始待确认；不能等到业务关联后才使记录出现在主列表。平台详情保留在来源主档，费用确认仍独立。

货拉拉订单列表接口 → Integration保存原始列表内容 → Order保存或更新本地订单摘要 → 按平台订单号获取详情 → 保存原始详情及本地详情展示数据 → 本系统列表、详情查询本地已保存数据。

人工订单关联由Order保存，人工员工关联由Integration保存并引用HR员工。同步字段与人工关联关系分别更新。员工或订单尚未关联、平台订单未完单、费用缺失均不是订单入库失败的条件。

列表摘要先提交，详情失败按单记录重试；不能在同一大事务中因一笔详情失败回滚整批列表。不把“人工关联完成或费用已确认”作为来源同步成功的判定。创建本地运输记录失败需要明确失败并重试，不能谎报成功。

## 2 当前代码已存在的基础

以下为本机源码核对结果，并非V2方案已完成的声明：

| 当前对象 | 现有用途 | V2需要调整的方向 |
| --- | --- | --- |
| integration_raw_landing | 保存订单list和detail原始内容及员工原始资料 | 保留；列表与详情保存和失败情况分开标识，可按单重试 |
| order_logistics_import_order | Excel/API来源待关联记录，source_json、latest_source_json、cost_id等 | 扩展为本地货拉拉订单主档；本地完整列表与详情独立于成本生成状态查询 |
| integration_external_object_mapping | 平台员工到HR员工的对应关系 | 继续复用；通过平台员工目录区分staff_id与订单user_id，避免只按姓名认人 |
| integration_sync_task / integration_sync_run | 同步任务、执行状态与计数 | 增加或调整列表已保存、详情已保存、详情待补、失败计数 |
| integration_manual_resolution | 人工关联处理记录 | 继续记录人员关联、更正及解除原因 |
| 现有物流费用与审计记录 | 成本确认依据、业务分摊及状态 | 保持独立；不能用其状态替代平台订单状态或关系状态 |

当前Order来源表的state主要表达UNMATCHED/GENERATED，cost_id也将关联与费用生成绑定。这不足以直接表达“平台订单已经入库但尚未关联业务订单”的完整台账，本期应拆开状态和关系，不能仅改页面名称。

## 3 精简存储设计

优先复用现有数据表，不另外建立一套重复的货拉拉订单库：

1. 扩展现有order_logistics_import_order，承担平台订单来源主档，自动引用到现有物流运输记录；主档不是第二套业务台账。名称可为兼容保留，业务界面统一称物流运输记录，平台信息在详情分区展示。
2. 人员资料复用Integration原始员工数据，人员关联复用integration_external_object_mapping，不新增独立员工、部门、人员关联三套表。
3. 业务订单关联需要独立、多对多持久化。建议仅新增一张平台订单—业务订单关系表；费用单sources_json不是本期订单关系的唯一存储位置。
4. 原始返回继续在Integration保存；Order通过版本化服务契约取得适合本地展示的数据。不通过跨库SQL读取Integration、HR、CRM业务表。

### 3.1 本地订单主档应保存的信息

| 分组 | 建议内容 |
| --- | --- |
| 身份及幂等 | 本地ID、tenant_id、企业／连接标识、货拉拉订单号；平台单号以字符串保存 |
| 可查询摘要 | 平台状态、下单／用车／完成时间、平台下单用户标识、车型、订单费用、已付、未付、退款及最近同步时间 |
| 列表原始内容 | 最新有效列表JSON及摘要校验值 |
| 详情内容 | 最新成功详情JSON，包括地址点、费用项目、司机车辆、回单等实际返回字段 |
| 同步情况 | 列表保存时间、详情成功时间、详情状态、最近尝试时间、失败原因分类、重试次数 |
| 业务分类 | 人工确认的运输类型，独立于来源更新 |
| 并发及审计 | revision、创建及更新时间；同步服务身份与人工操作身份分别记录 |

常用查询字段结构化并按实际查询增加索引，数组和扩展字段使用JSON。原始JSON落地不等于产品列表与详情已经实现，必须有本地读取契约和展示字段。

现有唯一键是tenant_id、carrier_order_no；V2应在核对存量数据后明确企业维度的唯一约束，目标为企业租户、来源企业／连接、平台单号一致。不得假设不同企业平台单号永不重叠。升级用新迁移，不能改已执行V67/V69原件。

### 3.2 独立订单关系

关系至少保存：本地平台订单ID、企业范围、业务订单类型、业务订单编码／标识、关联状态、创建及更正人和时间、revision。

同一平台单和同一业务单只有一条有效关系；一对多、多对一均允许。展示客户、业务员和部门通过现有业务订单查询契约取得；已确认成本使用自己的归属快照，不因关系或人员当前部门改变而被静默重算。

更正与解除保留审计。平台原单不因解除关联被删除；重新同步也不重新创建人工关系。

## 4 平台、同步、关联和单据状态必须分开

| 类别 | 含义 |
| --- | --- |
| 平台订单状态 | 货拉拉返回的进行中、完成、取消等；保留原状态码和业务显示名 |
| 同步状态 | 列表已保存、详情待补、详情已保存、重试失败等内部处理状态 |
| 人工关联状态 | 订单关系未关联／已关联；员工关系未关联／已关联，分别判断 |
| 单据状态 | 本系统待确认／已确认／已作废，沿用原成本流程 |

原有费用单DRAFT/CONFIRMED/VOID仍只代表费用审核，不扩散到平台订单。来源缺少价格、存在退款、未完单可以影响后续成本资格判断，不能影响平台原始订单和详情保存。

## 5 更新与防覆盖

同步更新只操作平台字段及同步元数据；关联接口只操作业务关系及人工运输类型。分开版本检查，避免一份全对象更新把另一类字段覆盖。

详情失败时保留上次成功详情，标注最后成功时间和最新尝试结果；不能用空对象覆盖完整旧详情。最新平台列表摘要可以更新，但不据此伪造缺失的详情字段。费用变更与已确认成本之间保留原确认依据，由成本流程处理，不在同步事务中自动撤销或确认成本。

更正员工关联后，本地订单视图可以按平台人员映射展示新关联；历史成本中的人员和部门快照仍保持原值。两类关系分别可用，不要求先完成人员关联才能保存订单关系。

### 5.1 外部接口能力限制

- 企业列表近3年、详情近1年为当前文档范围；不能承诺有列表就必有历史详情。APP列表近3个月，不能套用企业范围。
- 员工目录单独同步；订单请求不因员工方法失败而跳过。企业目录code／staff_id与订单user_id通过员工详情对应，不从联系人推断。
- 装卸货图、实际里程等需额外开通的字段按可用性保存；不将其列为强制必填。
- 所有快照注明来源方法与版本。APP与企业列表／详情的结构、时间类型、金额字段分别适配。
- 未取得既有平台订单的通知覆盖保证前，采用查询补同步；不只根据最新用车日期过滤来假装账单增量。

## 6 金额与字段规则

- 官方以分提供的金额使用精确小数转换到元；null保留缺失，明确0保留0.00。
- 平台订单总费用、已付、未付、退款、优惠、赠金分别保存，不能把其中任一字段无条件当作我方已确认成本。
- 来源返回多少有效业务字段就保存并按权限展示，不要求在前端补填其替代值。
- 平台联系人不等于平台员工；staff_id、user_id及订单联系号码分别处理。
- 平台返回限时司机信息、照片或链接时，记录取得时间和可用性。图片及回单是否需要长期留存、可否下载保存，以实际授权和业务要求确定，不承诺只存URL即可永久访问。
- 单号全程字符串，不能用浮点解析；接口确需数值参数时采用可验证的精确类型，禁止长整型溢出或科学计数。

平台金额、优惠、退款、赠金不得以未经核对的公式合并为净成本；企业旧pay_status停止维护，不作为结清唯一依据。最终口径按相同原单的网页、API及账单核对后固化在适配层。

## 7 查询与性能

本地订单列表使用分页、数据库筛选和索引；详情查询本地最新成功数据及人工关系。页面查询不对列表每行实时调用货拉拉、HR或CRM。

按批量接口或本地投影填充关联人员和原单摘要，避免N+1远程调用。详情补同步可独立排队；自动同步、指定单号重试均使用相同幂等键。请求限速、分页和历史窗口按当前官方能力设置，代码配置不放入业务页面。

## 8 方案实施核对

- 列表入库成功、详情失败时，已经能查到该订单。
- 查询和详情断开平台访问后仍能读本地内容。
- 同步原始字段更新，不覆盖人工订单和员工关系。
- 多对多关系独立于cost_id，不以费用确认完成为保存和查询前提。
- 当前来源原单已生成成本时保留历史引用；升级不能制造重复原单或重复费用。
- API与Excel对同一平台单更新有明确来源规则，字段缺失不能抹除完整旧数据。
- 迁移、页面权限和导出权限经隔离检查后，企业应用开通再做真实联调。

## 9 统一主列表与手工记录保护

1. 物流记录保留本系统ID、费用单号、来源、源订单标识、单据状态。平台来源以企业和平台单号去重，建立源订单到本地运输记录的唯一引用；手工记录保留原有ID。
2. 列表、详情均从本地持久化数据读取；平台详情与主记录通过ID引用，不在页面实时拼接第三方接口。
3. 平台源字段只更新平台记录；人工类型、关联、负责人、附件及审核状态单独更新，防止同步覆盖。
4. 已确认费用保留确认时快照；源金额变化只更新平台事实并标记复核，不自动重写BI已确认事实。
5. 手工货拉拉记录仅有明确平台订单号时可识别重复；没有源标识的历史数据不做金额或姓名模糊自动合并。作废后删除保留源唯一标识与审计，不能因再次同步复活成重复成本。
6. 正式结构按前向迁移推进，已执行的V迁移不可改写；不能用虚假“已生成费用”状态冒充记录已入库。


## 10 V2.5 账单、分项及凭证自动保存设计

复用来源主档的成功详情快照、既有成本确认记录及附件能力，本轮不建议为账单汇总、每种费用和每种凭证各建一套业务表。查询所需金额保留结构化摘要，费用数组及凭证关联保留在版本化详情中；原始响应继续归Integration，Order读取其版本化展示契约。文件复用既有附件元数据和存储，不在业务页面暴露源报文或存储路径。

### 10.1 身份、版本与部分失败

- 以租户、来源企业／连接、平台订单号标识同一账单所属的运输记录；平台单号全程字符串。同步、Excel、重试共用去重规则。
- 在有效完整详情范围内，账单摘要与费用分项一起提交；保留平台更新时间、内容指纹和成功取得时间。相同内容仅更新同步尝试信息，不追加新账单或费用；有变化保存新快照，保留确认时引用的旧快照。
- 费用明细按来源稳定行标识保留；没有来源行ID时保留成功快照中的原始数组与序号，整组版本化替换，不能按费用类型或名称作唯一键，也不能每次同步向旧费用数组追加。同一类型允许多条有效费用。
- 缺字段、权限受限、请求失败与平台明确返回空列表分别处理；不完整响应不能抹除旧成功账单。只有已核实完整响应的显式变更才更新对应内容，不能把“未返回”推断为“已删除”。

### 10.2 凭证的自动取得

平台费用项的图片／文件与原费用行关联，支持一项多份。记录来源标识、源地址、费用引用、取得时间、凭证状态、文件标识及内容校验值；同一文件重试不重复存储。链接可能有时效，不能只保存URL并宣称已长期留存。

账单提交后可靠安排文件补取，逐文件限速、校验格式与大小、失败重试。取得授权允许留存的文件后，保存到既有私有附件存储，按租户、Order物流记录及来源区分；下载继续使用既有鉴权与受控地址。不把访问令牌、签名参数或原始敏感链接暴露到业务页面和日志。实现位于Integration独立凭证队列，原文件成功保存COS后再通过Order领域接口登记引用；Order暂不可用时只重试引用投递。

平台未提供凭证显示暂无；已提供但尚未成功取得显示待获取；取得成功后支持查看下载。失败不能阻断账单保存、删除已留存文件或要求业务手动补录金额。人工上传附件单独记录来源及上传人，不覆盖平台凭证。是否能取得原图、具体文件权限及实际期限仍以企业真实授权联调为准。

### 10.3 统计唯一口径

平台账单总计是来源事实；费用分项、支付、退款、赠金各自保留，不能再作为独立成本累加。适配层逐来源核对金额含义、层级和正负号；不能盲目把所有费用数组层级相加，也不能在已经折后总额上再次减优惠或退款。

确认时保存所引用账单快照、实际我方承担金额和业务分摊快照；同一运输记录仅有一个当前有效确认结果。同步仅更新平台事实，不直接修改已确认成本或发出第二笔成本。费用或退款口径变化标记需核对，付款进度与新增凭证不自动改变成本。撤销使旧确认失效；重新确认以有效版本替换，不累加两次。

BI继续读取领域发布的有效确认事实，不同时累加来源订单金额、费用项、支付记录和业务单分摊。分摊合计应等于本笔实际我方承担成本，不能每个关联销售单各计整单金额。原型仅演示业务交互；正式实现的验证范围及尚不能验证的企业真实接入见第11节。


## 11 实施补齐与验证范围（2026-11-10）

本轮对应产品验收项A07、A16、A25、A26、A28补齐以下边界，不增加业务页面配置项或新业务表：

- 员工目录暂不可用时，综合同步仍继续保存订单列表和详情；同步记录单独保留员工目录失败原因。仅同步员工目录的失败仍报告失败；无法取得或刷新授权令牌时不会伪装订单同步成功。
- 详情回执未提供或异常返回费用、路线、回单及凭证数组时，保留之前成功取得的内容。金额未提供与明确0分别处理；已取得金额不会因缺项清空。最终费用仍依据当前完整账单资格检查，不凭历史值自动确认。
- 以合并后的账单金额和费用组成判断变更。仅数值精度、支付进度、员工关联或凭证变化不生成费用差异；真实账单变化保留旧账单和新账单，不能覆盖已确认成本。
- 人工员工关联与Integration既有出站事件在同一事务保存。后台通过版本化Order接口更新该用户对应的全部运输记录，失败自动重试；更改、解除及乱序重试以较新关联版本为准，旧同步批次不能恢复已经解除的关联。只修改当前下单人关联，不改业务单、账单历史、已确认金额和部门／业务员成本归属。
- 复用integration_outbox_event；不新增员工或关联业务表，也无需为本轮新增数据库迁移。关联事件与订单同步相互独立，保存不等待外部调用。

本地验证使用隔离H2库及服务契约测试，覆盖目录失败后仍保存真实结构的订单回执、多笔运输记录的员工关系更新、解除及旧版本重放、重试租约、租户和连接隔离、旧JSON兼容、缺项回执保留、真实金额差异、金额分摊、只读及状态保护。测试中的平台回执和人员均为隔离样本，未写入共享DEV业务表。

货拉拉企业应用目前尚未上线。真实OAuth、企业订单字段覆盖、平台凭证下载并归档自有COS，以及真实关联后BI核对，需企业应用上线并在Integration运行环境配置凭据后继续；不能以隔离测试替代真实接入验收。

## V2.6 企业订单支付字段映射

本企业确认接入 e-order-detail。以下路径在 data 内；原始响应落地 Integration，规范化字段和金额在 Order 的既有来源JSON保存，不新增付款表。

| 官方字段路径 | 本地字段 | 页面 |
| --- | --- | --- |
| order_detail_item.order_item.order_display_id | CarrierOrder.orderNo | 第三方订单号，字符串 |
| order_detail_item.order_item.order_status | CarrierOrder.status、raw[平台订单状态码] | 平台订单状态，保留码和对应名称 |
| order_detail_item.order_item.price_fen | SourceFacts.billAmount | 账单总计，分转元 |
| order_detail_item.order_item.paid_amount | CarrierOrder.paidAmount | 已支付，分转元 |
| order_detail_item.order_item.unpaid_amount | SourceFacts.unpaidAmount | 未支付，分转元 |
| order_detail_item.order_item.refund_amount | SourceFacts.refundAmount | 退款，分转元 |
| order_detail_item.order_item.order_price_arr[] | SourceFacts.fees[] | 费用项目、金额、凭证 |
| 费用项 bill_name／price_fen／img_urls | Fee.name／amount／vouchers | 平台费用只读；凭证转存自有COS后展示 |

订单与费用项的 pay_status 均已被企业官方文档标为2025-09-04起停止维护，不作为当前付款状态。展示状态由上述有效支付金额按PRD推导；缺失、退款或对账不符保留待核对。平台付款状态不能写成手工选择值，不借用费用主档中 payment_status_code 的默认 UNKNOWN 作为平台业务显示。付款进度变化不进入成本差异指纹；成本确认仍使用自己的金额快照。

APP接口 u-order-detail 的 price_info[].pay_status/pay_status_name 是逐项费用状态，结构与本企业接口不同，本期不接入也不套用。企业接口后续若提供新的有效状态字段，需要再核验映射。

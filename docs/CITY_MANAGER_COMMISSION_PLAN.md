# 考勤、薪酬与绩效：独立规则与月度工资条

更新：2026-10-15。本文件替代此前“发布薪酬方案、绑定适用人员”的实施设计，采用用户最新确认的独立规则流程。已实现代码与 DEV 验证范围见末节，不能等同正式业务验收。

## 1. 业务操作

1. 在员工档案维护固定薪资或各档位的底薪、绩效基数及生效月份。
2. 分别维护考勤、绩效、补贴、提成规则。公共规则按部门、人员身份、生效月份匹配；不再要求建立方案或给员工绑定方案。
3. HR 在月度薪酬选择月份及员工，手动批量生成工资条。
4. 核对底薪、绩效、补贴、提成、历史更正及来源异常；必要时填写调整及原因，再确认、登记发放。
5. 来源变化通过检查提示重算；已发工资保留，后续差额使用更正记录。

应发工资＝底薪＋绩效＋适用补贴＋销售提成＋城市总提成＋经核定的历史更正；本月核算金额＝应发工资－其他扣款。缺卡、缺拜访及回款未达标扣减已包含在绩效金额中，不再次计入其他扣款。每人每月一张工资条，多城市管理只展开提成来源，不重复发底薪或补贴。

## 2. 页面职责

| 入口 | 维护内容 | 核算使用方式 |
| --- | --- | --- |
| 员工档案／薪资标准 | 固定底薪与绩效基数，或金银铜三档各自的底薪与绩效基数、身份、生效月份、底薪及绩效折算 | 根据当月有效标准计算；三档区间读取公共绩效规则 |
| 考勤规则设置 | 部门工作日历、跨天窗口、特殊工作日、休息日、过程豁免、月度应出勤天数 | 只配置薪资统计规则；原始打卡和拜访来自 Sales |
| 绩效规则设置 | 打卡与有效拜访、回款达标两项绩效权重及缺项扣减、有效拜访条件、新人保护、阶段目标、金银铜区间；城市总动态指标及阶梯 | 规则决定算法，员工档案提供金额基数 |
| 指标设置／薪酬绩效目标 | 员工当月回款或城市总指标目标，保留现有经营指标入口 | 未单独填写的销售目标使用入职阶段默认值；城市总目标缺失则待核对 |
| 补贴规则 | 补贴项目、金额、身份、部门、生效期、折算 | 与底薪独立；无补贴明确保存空项目，不将未配置当作零 |
| 提成设置 | ERP 分类及子类、排除分类、SKU、受益角色、比例／数量单价、管理归属及标准取值日期 | 整单付清后按历史规则计算；未配置商品进入待核对 |
| 城市总管理 | 人员、城市、任期、交接与历史 | 一人可管理多城，同城任期不重叠；不在这里编辑提成比例 |
| 月度薪酬 | 批量生成、来源检查、工资条、调整、确认、发放、明细导出 | 展示计算依据与异常，未完成核定不能当作已发工资 |

## 3. 自动规则编码与版本

- 新增规则由 HR 后端调用现有 `BusinessCodeGenerator`、`BusinessCodeRule.daily("PCR", 6)` 生成业务编码，形如 `PCR20261015003777`。HR 不录入或修改编码。
- 同一规则调整后沿用业务编码和规则 ID，生成新的不可变版本 ID。工资快照关联具体版本 ID，业务检索使用编码。
- 保存请求使用幂等请求号，网络重试返回原记录；租户锁与数据库唯一约束防止并发冲突。编码在租户范围内唯一标识规则族，版本组合唯一。
- 规则名称可以调整，编码不随名称变化。不能依赖名称关联工资、商品或员工。
- 公共规则同范围同时段冲突会阻止保存；版本调整从未来月份生效。新版本到期后不恢复旧版本。历史工资保留实际命中的版本。
- 每个新增 API/model 使用独立文件；业务金额用 BigDecimal/DECIMAL，所有规则、查询、唯一约束携带租户。

## 4. 已确认的业务计算口径

### 销售

- 打卡与有效拜访绩效权重初始40%，回款达标绩效60%，均可配置。底薪和绩效基数均从员工当月档位取值，两项金额分别维护。
- 每日7次打卡，缺1次扣20元；3次有效拜访，单次至少10分钟，缺1次扣30元。每天独立核算，不能跨日抵扣。
- 入职首个自然月过程及回款均免考核，底薪和绩效基数按铜牌；第二个自然月回款目标5000，第三个自然月起7000。可按规则调整，个人当月目标可在指标设置核定。
- 回款业绩为“当月首次整单付清的订单基数”。6000元订单上月收2000、本月收4000，本月计6000，不按本月逐笔回款计4000。
- 过程实发=max(0，绩效基数×过程权重－逐日缺项扣减)。结果实发=结果绩效预算×min(1，实际业绩÷目标)。新人豁免优先于目标考核，超额不额外增加结果绩效。
- 公共档位初始为铜牌[0,10000)、银牌[10000,15000]、金牌(15000,+∞)，端点明确、区间完整；各档底薪与绩效基数由员工档案分别维护。
- 初始销售补贴为交通500、话费150、电脑100；城市总及总部不自动套用。补贴规则可独立变更。

### 城市总

- 多城市任职独立维护，绩效按人员汇总；本人订单可以同时取得销售和城市总两种提成，不因此自动适用销售底薪或补贴。
- 工资由固定底薪＋绩效基数×综合系数＋商品提成组成；不套用销售补贴。先汇总各指标的完成率×权重，再匹配综合系数。初始区间为[0,100%]按实际完成率、(100%,+∞)按1.2；系数区间与封顶可配置。保护期按入职日起顺延日历月，保护期内外分段计算。
- 城市范围内金额按订单去重，门店按稳定 ID 去重。动态新增指标必须选择已有事实来源或明确人工核定，不把指标名称当作已经接入的数据源。

### 提成与历史更正

| 初始商品范围 | 销售 | 城市总 |
| --- | --- | --- |
| ERP 方便面分类 | 商品回款基数4% | 商品回款基数1% |
| ERP 台球周边，排除台呢 | 商品回款基数10% | 商品回款基数2% |
| 台呢及其他业务 | 由业务另行配置或明确排除 | 由业务另行配置或明确排除 |

- 混合订单必须整单付清，数量提成也遵循这一约束，不提前生成部分回款提成。只归入整单付清所属月份，历史遗漏由更正处理，不能自动把所有历史未发提成叠加到本月。
- 页面按商品标准一行展示销售提成、城市总提成与核对合计；合计不作为第三笔提成。支持分类、SKU 单独配置以及所选标准批量修改。
- 分类、商品、规格用 ERP 稳定 ID，保存时校验引用存在及单位有效。专项 SKU 优先于最具体分类，同级冲突待处理。
- 管理归属日期和标准取值日期分别支持订单日／整单付清日。交接后回款不必改变原管理归属，依订单执行政策及历史任期判断。
- 本期只使用现有订单金额与商品分摊依据，不新增税费、余额拆分或商品退款分配功能。
- 退款、撤销和纠错通过现有工资更正流程，由 HR 根据原人、原规则和原明细核定；已发工资不覆盖，不把前任退款扣给新任。

## 5. 来源、缺失与权限

Portal → Gateway → HR。HR 通过版本化服务接口读取 Order 的订单付清及商品金额、ERP 分类规格、Sales 原始打卡拜访；HR 不跨库查询其他领域业务表。

原始销售打卡由 Sales 服务负责。HR 手动修改实际出勤不会伪造打卡或拜访次数，请假审批也不自动覆盖实际出勤。日历与月度应出勤不一致须核定；数据源不可用显示待核对，不当作零业绩或缺勤扣款。

规则维护、员工薪资维护、考勤修正、工资确认和发放使用现有权限及数据范围；每次变更保存原因和审计。新月份按当前有效规则生成，已有确认／发放记录不会被新规则覆盖。

## 7. 月度薪酬列表整合（2026-10-15）

- 列表默认“工资核对”，每人一行展示底薪、绩效、补贴、提成、补发补扣、其他扣款、应发与本月核算金额；员工和核算金额固定，部门与身份放在员工名下。可切换“发放情况”查看已登记发放、待发和最近发放日期。
- 待核对状态在业务页面统一为“待处理”；列表只展示问题类别数量，点击打开对应工资条的处理指引。底层状态仍为 REVIEW／READY／CONFIRMED／PAID，不新增审批节点。
- 新增 `GET /api/v1/hr/payroll/summary`，由 HR 按租户、阅读范围、月份、员工和部门做数据库汇总。状态页签数量不受已选状态过滤影响，合计受状态过滤影响；统计覆盖全部匹配记录，不是当前页。
- 金额合计仅包含状态完整且应发与核算金额均为有效数值的工资。待核定与零金额分开表示；无完整结果显示“—”，并展示完整人数与待核定人数。部门按该月工资快照过滤，避免员工当前部门变化影响历史月份。
- 新增批量确认与批量重算，明确选择本页人员。执行前展示可处理和跳过原因，逐人调用现有事务接口，保留版本、来源、权限及状态校验；失败独立反馈，支持停止后续处理。确认不自动登记发放，不覆盖已确认／已发工资。
- 工资条明确展示打卡与有效拜访绩效、回款达标绩效、权重、绩效内扣减、补贴月度标准及本月金额；城市总展示加权完成率与综合系数。导出沿用当前筛选范围和核算快照，区分待核定与零值。
- 已在已登录本地页面验证北京马南、许少华的月份列表、员工筛选、汇总同步、未完成工资批量确认拦截、两人批量重算成功及工资条。两人重算仍有来源问题：历史整单付清业绩依据、历史提成标准及马南当月部门归属待核定；未确认、未登记发放。

## 8. 真实来源核算与规则补齐（2026-10-15，最新实现）

本节取代第 6、7 节中旧页面及“打卡审核/时长不齐阻塞核算”的阶段性说明。

- 工资列表改为员工、部门、薪资类别、月份和各项金额的明细表。工资条按工资汇总、提成明细、绩效明细、规则依据与调整、发放与更正、操作记录分开展示；不新增薪酬组或方案选择。生成时自动匹配各项独立规则，筛选选择只处理筛选出的未锁定员工。
- Order 使用有效回款单（RECEIVED/CHECKED，未删除）累计金额取得首次整单付清日期，HR 只计入该日期落在薪资月内的订单。早月下单、当月付清可以计提；混合订单部分回款不计提；后续回款不移动首次付清月份。已有确认提成按订单明细与受益角色防止重复释放。
- 导入订单无归属快照时使用订单中已存的销售与城市；存在待审核归属快照或本地订单缺少冻结归属时仍保留真实异常，不改取当前客户归属。城市总团队提成使用受益城市总自身适用部门的规则，避免因团队销售任职历史缺失而误判为缺规则。
- 来源已关联并成功返回时：未通过审核、无有效客户标识的打卡不计达标；审核通过但无可信时长的记录可计打卡，不计有效拜访。每日不足次数自动按配置单价扣减，以打卡与拜访绩效额度为上限，不扣回款绩效。每日保留达标数、缺少数和扣减依据，不生成逐日待处理事项。来源调用失败、账号未关联仍不能伪装为零完成。
- 提成实际明细保留 ERP 分类/规格/单位、订单日/整单付清日、数量/金额基数、比例或单价、规则编码与版本。分类→商品→订单汇总使用后端持久化金额；完整结果隐藏无意义的零待核定列。工资总额、Excel 与明细采用相同快照。

# 销售作业与手机门店开发发布（2026-11-18）

## 发布范围

## 发布前检查

- 工作分支 dev；先 fast-forward 同步远程物流提交，再提交销售改动，不使用强制推送。
- 正式服务由 `rg-scdp@<service>` systemd 单元运行，JAR 位于 `/root/rg_scdp`。旧部署文档中的服务数量和脚本不是此次执行依据。
- 正式数据库、服务包、环境配置和域名入口已做服务器侧私有备份。
- 根据实际表、列、索引核对缺失迁移，不以旧 Flyway 历史直接推断结构，不自动 baseline/repair。
- 生产缺失结构对应 CRM V35–V41、Integration V28–V33、Sales V31–V43；在导出的无业务数据结构副本上用 MySQL 8.0.46 演练成功。与 DEV 比对后，业务表字段齐全；保留正式库既有 Flyway 历史。
- 同步检查已合入 dev 的其他服务：Order 缺失 V67、V69–V74、V76–V78，V68/V75 已存在；ERP 缺失 V46；BI 缺失 V29。上述增量结构也已在正式结构副本上演练通过。正式运输成本表为空，V76 不会转换任何现有费用记录。
- 订单/ERP/BI/HR 也完成独立备份；大审计记录需将 mysqldump 客户端 max-allowed-packet 设为 1G，最终压缩包完整性校验成功。
- 未导入 DEV 业务数据、测试账号或认证会话。

## 构建与部署验证

先运行 `./mvnw verify` 完整验证，再以 `-Pscm-prod clean package -DskipTests` 单独制作生产包，排除开发及本地环境配置。开发配置测试需要读取 local/dev YAML，不能在排除这些文件的生产资源集上运行。发布包记录源代码提交和 SHA-256，上传后复核校验值。

按服务顺序停旧进程、原子替换 JAR、启动并轮询健康接口；失败时恢复上一份 JAR。数据库采用增量迁移，不通过恢复整库回滚上线期间业务数据。部署后核对服务稳定性、新日志及 HTTPS 入口。

手机独立安装包、生产角色与规则发布、真实路线里程验收分别记录结果，不能以服务健康检查替代端到端验收。

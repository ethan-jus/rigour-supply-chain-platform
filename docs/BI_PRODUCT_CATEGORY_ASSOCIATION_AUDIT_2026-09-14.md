## 已证实根因与修复

1. **这批分类待核对不是 BI 把已有商品主键丢了。** Order 源行就没有商品/SKU主键，但 ERP 当前商品目录并非普遍缺分类。仅凭原商品名称相近不能证明应归哪个 ERP 商品、SKU或分类。保留金额、订单与待核对状态，交由业务补关联。
2. **商品排行确实漏金额。** 原 `productSalesRanking` 以未删除的 `bi_product_dim` 为起点，无法承接无主键、主键无投影或商品已删除的订单行。现先按租户和原期间/城市/销售/客户类型/来源取行，再把不能关联有效商品的金额单列，不按名称合并到某个商品。移除原 500 组静默截断，避免待关联组及长尾商品金额被截去；图表显示条数由展示层处理。
3. **分类排行与报表关联口径不同。** 报表已优先使用 ERP 商品投影，而分类排行直接使用订单行分类快照。现统一优先使用当前商品投影分类；当前分类被清空时不能回退到陈旧分类。未知或删除的分类仍按待核对保留，不凭名称补父类。
4. **父类承载历史事实不能消失。** 即使某父类没有当前有效商品，只要所选范围仍有直接归属该父类的事实，就保留这部分金额；它不是对子分类汇总再加一次。

查询仍只读 `rigour_bi`。未改变日期聚合、比较、目标、回款分摊或来源投影流程。默认不分摊的报表口径不变。

## 下钻与业务补关联

- 新增商品待关联组：`dimensionCode=UNKNOWN`、`dimensionName=商品关联待核对`、`categoryCode=UNKNOWN`。这是异常汇总标记，不能作为 `productId` 查询 ERP。
- 现有销售订单页：`/supply-chain/order/sales-orders`。`SalesOrderView.vue` 的 `applyRouteQuery` 已支持 `dataQualityStatusCode=NEEDS_REVIEW`、`orderDateFrom`、`orderDateTo`、`regionCode`、`ownerEmployeeCode` 和 `drillLabel`。日期参数使用 `YYYY-MM-DD`，不是 BI 的 `from/to`。
- 核查时该列表查询与 Order API **尚未支持 `sourceSystemCode` 筛选**，`sourceStatusCode` 是来源状态而非来源系统。不能只在链接拼接 `FEISHU` 就声称订单列表已按来源过滤。页面下钻由主线程整合，本补丁不改 Portal。
- 已有人工更新接口：`PUT /api/v1/orders/sales/{id}`，使用 `SalesOrderCommand.lines[].productId/productVariantId` 和 `revision`；需要 `order:write`。前后端均允许飞书草稿编辑，非草稿飞书订单不能人工覆盖来源投影。此次 60 笔符合草稿条件，但不等于自动修复已经执行。
- 业务需确认真实商品、规格、单位与原单据。当前编辑页选商品/规格会在 `applyVariant` 中将单价设为 ERP 售价，且数量输入精度为两位；因此历史订单不能未经复核直接选择后保存，以免连带改变原成交数量、单价、优惠和销售额。现有接口是完整订单更新，不是仅补主键的专用接口。
- 其中一条待关联行的备注表明它是缺独立商品明细的多商品汇总占位；不能把它强行关联成单个 SKU。先补完整、可核对的实际商品明细，再通过现有受控流程刷新 BI。

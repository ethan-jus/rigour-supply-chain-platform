# BI 业务日期边界

2026-09-14。仅统一 BI 业务日解释，不迁移或改写源订单、回款、成本时间。

## 约定

- 业务日及目标月份使用 `Asia/Shanghai`。Portal 日历范围 `2026-09-01` 单日传输为 `2026-09-01T00:00:00+08:00` 至 `2026-09-01T23:59:59.999999+08:00`。
- API 继续接收和返回 `Instant`。上述区间在 UTC 中是 `2026-08-31T16:00:00Z` 至 `2026-09-01T15:59:59.999999Z`。显式传入的 Instant 区间不自动改成整日。
- Repository 仍以 UTC `LocalDateTime` 绑定 MySQL DATETIME(6)。日期分组、目标月份匹配和按日计算只在表达式中转换一次；不改变 WHERE 的 Instant 边界，也不偏移写入值、ETL 水位或身份有效期。
- SQL 针对当前现代中国业务日期使用 `TIMESTAMPADD(HOUR, 8, ...)`，不依赖 MySQL 时区表。Java/Portal 使用命名时区；不声称支持历史夏令时数据。
- 两期比较沿用相邻等长、微秒闭区间；单个北京时间业务日的前期仍为前一个业务日。回款仍是所选订单累计回款，现金入账趋势仍按 payment_time 分组，两者未混用。

## 覆盖

- 驾驶舱期间、快捷月份/年份、最新订单默认月、两期文字及明细日期。
- 销售、实际回款、城市成本日趋势，销售人员月趋势。
- 城市/销售目标月份数、已配置月份与订单实际值交集；刷新核对的默认本月及目标核对月份。
- 客户静默天数、逾期账龄、库存日均计算的日历差。
- 样例固定费用包含首尾业务日，金额规则和样例标识不变。
- 城市商品 Excel 文件名、区间、订单日期及同步时间统一北京时间；货币精度、字典单位、默认精确归属及手动分摊不变。
- 追加 UNKNOWN 商品保护：不传 productId 或快照商品名称，进入保留日期/城市/销售范围的 `NEEDS_REVIEW` 订单；不向 Order 伪传来源过滤。待关联金额保留，但不计入已关联商品数量。

## 源数据边界

- `FeishuSalesOrderImportMapper.businessDateInstant` 当前将纯日期及 Excel 整数日期编码为 UTC 00:00；带时间的值通过 `instant` 按显式偏移或默认来源时区转为真实 Instant。这是两种精度/语义，不能因时间恰好为零点就批量减八小时。
- 旧纯日期记录在北京时间中显示为同一自然日的 08:00，其业务日期仍正确，但不能据此认定销售实际发生在 08:00。BI 目前没有源日期精度字段，无法仅凭事实 Instant 还原这一差异。
- `DhbOrderSyncService.instant` 保留已有 Instant，未带偏移的来源日期时间按 `SOURCE_ZONE` 转换；Order repository 再统一存 UTC。此次不改这些导入或存储转换。
- 本轮未改 `BiReconciliationSourceNormalizer`、其测试、在线飞书组件/API或任何 Feishu Integration 文件。在线源采集方需要按原始字段精度核对日期，不能直接把纯日期正规化后的 Instant 与 legacy UTC 日期编码做八小时差异报警。
- 不改已执行迁移，不按商品名称猜补任何关联，不改变金额或回款分摊算法。

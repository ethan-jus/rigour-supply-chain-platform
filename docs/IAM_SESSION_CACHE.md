# IAM 授权缓存与销售 APP 会话设计

2026-11-12。仅 DEV，保留其他未提交改动，不发布生产，不删除临时打卡数据。

## 设计依据

- [Keycloak 缓存设计](https://www.keycloak.org/server/caching)：用户、角色及授权定义可以缓存，修改必须使其他节点旧缓存失效。我们复用现有数据库应用版本，任何节点每次读取当前版本后才能命中；没有新引入 Keycloak、Redis 或登录平台。
- [Microsoft MSAL 会话与令牌缓存](https://learn.microsoft.com/en-us/entra/identity-platform/msal-acquire-cache-tokens)：复用有效会话/令牌，优先静默恢复。APP 已有内存 access token、原生加密 refresh token、单次刷新合并；继续使用这些机制。
- [Auth0 Token 最佳实践](https://auth0.com/docs/secure/tokens/token-best-practices)：令牌声明精简，并设计过期与撤销；不把完整员工档案和可变授权定义装入 Token。

以上是成熟身份平台的公开设计依据，不推断任何未公开商业 APP 的内部实现。

## 数据放在哪里

| 数据 | 存放与复用 | 更新与安全边界 |
|---|---|---|
| APP 当前用户 | 内存 session：userId、tenantId、tenantName、username、displayName、roles、permissions | 登录/恢复/令牌刷新时从真实 `/me` 更新；失效/退出全部清除；只用于界面与请求上下文 |
| APP 员工档案 | 现有 salesProfile 按账号、租户、会话及权限隔离，状态和员工编码在当前会话复用 | 正式业务由 Sales→IAM/HR 再核验；不复制完整员工档案进 Token |
| refresh token | 既有 Android Keystore 加密存储 | 继续轮换、撤销、退出清理，不进入普通缓存或日志 |
| access token | 既有内存保存，有效期内复用 | Gateway/IAM 仍执行签名、会话和安全版本校验 |
| IAM 用户角色的授权定义 | 新增进程内版本缓存：本人角色、授权节点、数据范围定义 | tenantId + applicationId + userId + 数据库应用版本；每个缓存最多 1024 项，TTL 60 秒；撤权通过提交后的版本变化立即使下一请求失配，无需等 TTL |
| 最终允许/拒绝、订阅与账号状态、HR 员工有效性 | 不跨请求缓存 | 仍查当前真实状态，避免角色命中缓存却放过停用、到期、离职或会话撤销 |
| IAM 用户基础资料 | `/me` 中仍为一次轻量实时读取 | APP session 已复用，不因一条基本资料查询增加复杂的全局失效协议 |

服务端 `iam_auth_session` 继续保存会话标识、主体、状态、版本、有效期等安全事实；用户与角色仍是各自权威表的数据。客户端 session 的“当前用户快照”不是服务端授权依据，也不能通过修改本机角色来取得权限。

## 本轮实现

1. `VersionedIamReadCache` 存不可变定义。缓存只在授权读取作用域启用，管理写事务旁路，避免读取旧缓存或发布未提交数据；加载前后版本变化则拒绝混合快照，失败不缓存。多实例通过同一数据库版本识别变更。
2. `JdbcAppSettingsStore` 缓存已分配角色的授权节点集合；菜单启用、资源订阅与员工资格仍实时计算。`JdbcAppRoleStore.authorizationRoles` 用两组查询读取本人角色及授权节点，替代整企业角色管理目录的多次查询和人数/预览计算。
3. `IdentityAccessService` 在 ACTIVE 新授权模式只读基础资料与新模型角色权限，跳过随后会被丢弃的旧模型权限查询；旧模式入口保留。
4. APP session 补齐 `tenantName` 与 `roles`，从已验证 `/me` 填充；令牌刷新覆盖、退出/失效清理。不新增本地明文用户权限持久化。

正常角色/成员/菜单写入已有事务内 `settings.bump()`。人工 SQL、迁移若修改这些授权定义，也必须在同一事务推进应用版本；不能只改数据而沿用旧版本。本轮没有新增迁移、数据库写入或修改历史迁移。
